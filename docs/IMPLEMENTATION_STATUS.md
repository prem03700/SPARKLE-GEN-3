## Known limitations

- HTTPS encrypts bearer tokens and workspace data in transit. The private CA and current IP SAN have been verified, and the paired Android phone has completed the user-controlled browser/certificate setup. Each additional device must separately trust the CA before using the LAN URL. Do not port-forward this server or expose it through a public tunnel.
- Cross-device edits use revision checks and detect stale writes; a two-device API test now verifies a stale second-device write cannot overwrite the first device. When a conflict occurs, the user must reload the authoritative server copy. There is no automatic merge.
- Explicit Crossref scholarly metadata search is connected with authenticated access, rate limits, bounded results, DOI-only links, and audit logs that record query length rather than query text. Public web search and bounded on-demand HTML source retrieval are implemented through authenticated routes. Live upstream connectivity is not verified from this host (the direct provider probe returned a network error); paywalled and JavaScript-only content is not retrieved, domain labels are only weak hints, and users must independently verify sources.
- Knowledge imports text-readable files up to 250 KB as plain-text notes (Markdown/CSV/JSON are not parsed into structured records). Authenticated private-host extraction supports PDF (first 30 pages), DOCX, XLSX, and PPTX up to 250 KB, with bounded archive expansion/output. Scanned PDFs fall back to local English Tesseract OCR for at most five pages at 150 DPI; OCR results are explicitly marked as error-prone and require checking against the source. The OCR executable and English data are unpacked under the owner's `~/.local/opt/sparkle-ocr` directory, not installed system-wide. PDF/Office extraction uses host-side parsing and never executes document macros. Arbitrary code execution, shell access, robotics simulation, experiment execution, and external write integrations remain disabled.
- Personal Core integration is partly connected: root-level `personal_core.py` handles workspace snapshot validation/normalization, authoritative SQLite reads, revision-checked writes, and durable action proposals with explicit approve/reject decisions and audit records. Settings exposes a paired-device proposal queue. Approval creates one task, goal, or Knowledge record only for those explicitly selected proposal types; code/shell/robotics execution, external writes, and agent dispatch remain disabled. The JavaScript `src/core/personal-core/` memory and policy modules remain prototypes. The Python SQLite workspace remains the single source of truth; typed collection-change audit events now record collection names and before/after counts without logging record contents, and code-file records have trusted-boundary schema and size validation. Broader domain-specific use cases and safe execution adapters remain incomplete.
- No account system or cloud sync exists; this is a single-owner host with paired devices.
- The per-user systemd service starts with the user's systemd session; it is not a system-wide service that runs before login. The automated suite does not exercise physical hardware: user-confirmed phone voice and phone-to-server persistence have been recorded separately, while the reverse-direction computer-to-phone live UI update after the latest polling fix and voice stress/interruption/cancellation remain pending.

## R&D Lab: built-in simulation and experiment runner

The R&D Lab now includes a browser-side, deterministic simulation engine with four registered models: damped pendulum dynamics, a planar two-link robot arm, PID motor/setpoint response, and a simple swarm moving toward a target. The Simulation workspace provides Start, Pause, single-step, Reset, adjustable parameters, live canvas visualization, and telemetry. A five-point parameter sweep runs 1,800 fixed time steps per value and reports final, peak, and RMS metrics. Simulation runs and sweep results are saved in the existing `labDrafts` data collection and synced through the existing workspace persistence path when paired.

Important limits: these are mathematical demonstration models, not a substitute for calibrated physical simulation or real hardware telemetry. External engines (Gazebo/ROS 2, MuJoCo, Isaac Sim, etc.) are not connected yet. No user-supplied or AI-generated code is executed. The engine is intentionally an adapter-friendly first foundation; each future external engine needs an explicit, reviewed adapter, dependency setup, resource limits, and validation before being advertised as supported.
